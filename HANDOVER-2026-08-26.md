### Gateway indexing

The gateway now has the following design:

- Indexing is opt-in by configured server.
- Automatic refresh defaults to once per week: `604800` seconds.
- First automatic build can be restricted to maintenance windows.
- Schedule jitter, persisted retry backoff, and circuit protection are present.
- Foreground use preempts or pauses inventory.
- Adaptive AIMD pacing uses foreground errors, bad quality, latency, OPC health, host CPU,

- DA2 branch validation skips branch-only names that native navigation rejects with
  `E_INVALIDARG`, while preserving names that resolve to exact items.
- Yokogawa `SCS0130` / `U+0001` behavior is handled by typed DA2 malformed-branch
  classification, not a server-specific blacklist.

## 7. Root-cause analysis

The gateway has a process-wide mutex around its primary writable `IndexDb` connection, but
cleanup intentionally opens a separate SQLite connection so foreground read paths are not tied
to the primary writer mutex. That isolation is useful for reads, but it currently permits two
writers to contend.

The problematic sequence is:

1. `refresh()` calls `with_database()` for storage diagnostics.
2. On the first database open, `with_database()` calls `obsolete_servers()`, releases the
   primary mutex, and schedules cleanup for any `superseded` or `failed` server.
3. `refresh()` admits the build and starts an inventory handle.
4. `start_generation()` creates a new `staging` generation.
5. `refresh()` explicitly calls `schedule_cleanup(server)` again.
6. `cleanup_obsolete_generations()` opens a second connection and starts a write transaction.
7. Cleanup executes FTS, relational-entry, and generation `DELETE` statements even when a given
   batch has no rows to delete. On a multi-million-row database, the scan/transaction can hold
   the SQLite writer lock long enough to exceed the five-second busy timeout.
8. The active build receives its first progress event and `IndexDb::update_progress()` cannot
   obtain the writer lock.
9. The build fails with `database is locked`; failed-generation marking can fail for the same
   reason.
10. Cleanup finishes later. The old active generation remains intact, which explains why search
    and reads still worked.

The likely fix is to ensure cleanup never writes for a server while that server has an active
staging build. A robust implementation should also avoid opening a writer transaction when there
is no obsolete row to reclaim.

## 8. Recommended implementation

Make the smallest complete change that preserves startup recovery and post-promotion cleanup.
Do not replace SQLite with another database and do not remove cleanup entirely.

Recommended direction:

1. **Defer same-server cleanup while a build is active.**
   - Do not let the `with_database()` startup scan launch cleanup for a server that is about to
     build.
   - Do not let the explicit `schedule_cleanup(server)` after `start_generation()` launch a
     worker while the staging build is active.
   - Keep cleanup requests coalesced in `cleanup_tasks`; record a pending request if necessary.
   - Schedule the pending cleanup only after the build reaches a terminal state and
     `finish_build_for_control()` has released the build ownership.
   - Preserve cleanup for other servers and for abandoned/stale generations discovered at startup.

2. **Add a cheap obsolete-data precheck.**
   - Use a read-only `EXISTS` query scoped to the server and states `superseded`/`failed`.
   - If there is nothing to delete, return without beginning a write transaction.
   - Keep the existing bounded batch behavior when data does exist.

3. **Keep failure handling explicit.**
   - Do not silently ignore `update_progress`, failed-generation, or cleanup errors.
   - If cleanup is deferred or rejected because a build is active, log a structured reason and
     ensure the request is retried after the build.
   - Preserve the active generation if a build fails.

4. **Add a regression test.**
   The test should create an active generation plus obsolete rows, register a current staging build,
   request cleanup, and prove that progress writes for the staging generation succeed while the
   build is active. Then prove that cleanup runs after the build finishes and removes only obsolete
   rows. Use a deterministic synchronization primitive or a test hook rather than relying on a
   timing race.

5. **Retain existing cleanup tests.**
   Existing coverage around:
   - bounded cleanup,
   - separate-connection foreground reads,
   - cleanup errors,
   - transient cleanup retries,
   - shutdown,
   - generation activation,
   - obsolete/failed generation handling

   must continue to pass. Update or extend tests rather than deleting the current concurrency
   coverage.

6. **Update enduring documentation.**
   Update:
   - `README.md`: cleanup is deferred/coordinated around active builds and remains bounded.
   - `AGENTS.md`: cleanup cannot write concurrently with active build progress for the same server.
   - Any relevant gateway configuration or diagnostics text.

Do not add a Yokogawa-specific blacklist. The DA2 malformed-branch classification is the intended
compatibility mechanism.

index builds, monitoring, and other heavy operations overlapped. This was an operational
resource issue, not evidence that the gateway intentionally kills the terminal.

- Check host memory/swap before starting a full refresh.

before restarting it. Do not kill by process name; identify the exact PID and command line.
